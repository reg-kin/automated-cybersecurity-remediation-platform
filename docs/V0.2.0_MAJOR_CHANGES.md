# v0.2.0 --- Major Changes and Hardened Baseline

## 1. Purpose of this release

Version `v0.2.0` establishes the hardened remediation-platform baseline
of the **Automated Cybersecurity Remediation Platform**.

The release is a substantial evolution from `v0.1.0`. The work leading
to `v0.2.0` concentrated on four areas:

1.  making scanner normalisation and the Unified Security Finding
    contract more consistent and testable;
2.  hardening remediation and verification boundaries;
3.  improving deployment security and reproducibility; and
4.  strengthening release validation so that critical architectural and
    security properties are regression-tested.

`v0.2.0` remains a **pre-production release**. It provides the baseline
on which subsequent platform capabilities---particularly asset
management and risk contextualisation---can be developed.

## 2. Architectural principles preserved in v0.2.0

The hardening work did not change the platform's core division of
responsibilities.

### Scanner orchestrators

Scanner orchestrators remain responsible for parsing scanner-native
findings, deriving scanner-specific values, normalising findings into
the Unified Security Finding structure, and determining the
deterministic `finding_class`.

The release does **not** delegate finding classification or remediation
routing to the AI enrichment layer.

### AI enrichment

Ollama remains an enrichment component. AI-generated analysis is
advisory/contextual rather than the authoritative mechanism for
classifying findings or selecting remediation routes.

### Deterministic remediation

Remediation routing remains deterministic. A finding's class is mapped
to an authorised remediation capability, which invokes the appropriate
remediation implementation and verification workflow.

### Verification

The platform retains its two-stage verification model:

-   **Stage 1** --- immediate/local verification associated with
    remediation execution.
-   **Stage 2** --- authoritative scanner-based verification, immediate
    or deferred according to scanner semantics.

Scanner-specific verification behaviour remains scanner-specific.
Asynchronous Wazuh refresh behaviour is not forced into the same
execution model as scanners that can verify synchronously.

## 3. Scanner normalisation refactoring

A major body of work between `v0.1.0` and `v0.2.0` improved the
scanner-orchestration layer without erasing scanner-specific semantics.

### Shared Unified Finding construction

Common construction logic was extracted so scanner orchestrators can
build the canonical Unified Security Finding consistently. Shared
handling was introduced incrementally for Nmap, Lynis, OpenVAS, Trivy,
Wazuh SCA and Wazuh Vulnerability.

The refactoring also centralised genuinely common concerns such as UTC
timestamp handling, service-tier handling and required Unified Finding
fields.

The purpose was **not** to make all scanners identical. Scanner
identity, native parsing, target derivation, severity interpretation,
classification and verification behaviour remain scanner-specific where
required.

### Scanner regression tests

Normalisation regression coverage was established for all seven
supported scanner/integration paths:

-   Nuclei
-   Trivy
-   Nmap NSE
-   Lynis
-   Wazuh SCA
-   Wazuh Vulnerability
-   OpenVAS

These tests protect representative native-finding-to-Unified-Finding
transformations from accidental changes during future refactoring.

## 4. Unified Security Finding contract hardening

The Unified Security Finding schema and ingestion behaviour were aligned
and strengthened.

Major changes included centralising canonical required fields, aligning
the JSON schema with the actual ingestion envelope, validating findings
before downstream processing, and rejecting findings that omit required
scanner timestamps.

The release smoke suite includes a regression test checking that the
Unified Finding schema matches the canonical envelope and that invalid
ingestion data fails closed.

## 5. Remediation routing hardening

### Deterministic routing

The remediation controller was regression-tested to preserve
authoritative routing, approval semantics, Stage 1 verification,
immediate Stage 2 verification and deferred Stage 2 verification.

### Ansible Runner playbook allowlist

The Ansible Runner now uses a configured, fail-closed production
playbook allowlist. A caller cannot use the Runner API as an
unrestricted mechanism for selecting arbitrary playbooks. A requested
remediation must resolve to an explicitly permitted playbook.

A release-critical regression test protects this property.

## 6. API authentication hardening

The remediation API now requires mandatory Bearer authentication.

The verification gateway also fails closed and requires Bearer
authentication.

Regression tests ensure these controls remain mandatory rather than
becoming optional through future configuration changes.

## 7. Verification command-boundary hardening

### Input validation

Verification targets and metadata are validated before external commands
are executed. Regression coverage includes rejection of option-like
targets where unsafe, control characters, oversized metadata and invalid
timeout values.

Scanner-specific valid target forms are preserved. Legitimate URL and
image-reference targets are not destroyed by overly broad sanitisation.

### Request transport moved to stdin

Verification request data was moved away from command-line argument
transport and into structured JSON supplied over standard input.

This reduces exposure of request data through process argument lists and
gives the dispatcher a structured input boundary.

Dedicated regression tests cover valid requests, malformed JSON,
non-object payloads, missing required fields, control characters and
invalid metadata structures.

## 8. Deferred Stage 2 verification safety

The deferred verification workflow was strengthened and
regression-tested.

The reconciler requires fresh, authoritative scanner evidence before
concluding deferred Stage 2 verification. Runtime tests cover safe
rescheduling when evidence is insufficient, finding presence, finding
absence, scanner watermarks and lease-loss conditions.

This protects the platform from incorrectly treating the absence of
sufficiently fresh scanner evidence as proof that a finding has been
remediated.

## 9. Wazuh transport and configuration hardening

### Wazuh SCA API and Indexer

Wazuh SCA API configuration now requires HTTPS and mandatory TLS
certificate verification. Wazuh Indexer access similarly requires HTTPS
and mandatory TLS verification. CA bundle configuration is supported
rather than bypassing certificate validation.

### Redis endpoint

The Wazuh `custom-security-findings` integration now reads `REDIS_HOST`
and `REDIS_PORT`, with backward-compatible defaults of `127.0.0.1` and
`6379`.

This preserves the existing local deployment behaviour while allowing
the endpoint to be configured when deployment topology requires it. A
regression test verifies both defaults and environment-variable
overrides.

## 10. Ansible Runner security hardening

### Removal of NET_ADMIN

The Compose deployment no longer grants the Runner the unnecessary
`NET_ADMIN` Linux capability. The release smoke test rejects
reintroduction of `NET_ADMIN` and rejects privileged container
execution.

### Loopback remediation targets rejected

The Runner rejects remediation targets in the local loopback namespace,
including `localhost`, `*.localhost`, IPv4 loopback addresses in
`127.0.0.0/8`, and IPv6 loopback `::1`.

This prevents the remediation interface from directing Ansible execution
back into the Runner's own local environment.

### Dedicated non-root container identity

The Runner executes as the dedicated `ansible-runner` identity with
UID/GID `10001`, rather than as root.

SSH material is mounted read-only into the dedicated user's home
directory. Administrative privilege required on a legitimate managed
target is obtained remotely through Ansible `become`, rather than by
running the Runner container itself as root.

Regression coverage checks the dedicated non-root identity and read-only
SSH-material contract.

## 11. Application systemd services moved to non-root execution

The principal application services are configured to run as:

``` text
User=automated-remediation
Group=automated-remediation
```

This applies to `scanner-control.service`,
`ollama-wazuh-enricher.service`, `deferred-reconciler.service` and
`remediation-controller.service`.

The Ansible Runner retains its separate `ansible-runner` identity
because it represents a distinct execution boundary.

A release-critical regression test prevents application systemd units
from silently reverting to root execution.

Further systemd sandboxing and deployment-account provisioning are
intentionally treated as later deployment hardening rather than blockers
for this baseline.

## 12. Dependency and image reproducibility

### Python and Ansible dependencies

The root Python dependency manifest was completed and security-sensitive
dependencies were updated and pinned. The Ansible Runner's Python
dependencies were explicitly pinned, and the redundant Debian Ansible
package installation was removed.

### n8n

The deployment no longer uses the floating `latest` n8n image tag. It is
pinned to the tested release used by the repository deployment contract.

### Ansible Runner base image

The Runner base image changed from:

``` dockerfile
FROM python:3.11-slim
```

to:

``` dockerfile
FROM python:3.11-slim@sha256:9534e5a8e315485d4061ed659af0fd78a284c015f9b73661b41d6bab25604534
```

Using the OCI image-index digest makes base-image resolution
reproducible while retaining the readable tag and normal multi-platform
semantics.

The release smoke test rejects regression to the unpinned base-image
tag.

## 13. Deployment configuration and project identity

Deployment configuration and documentation were aligned with the public
open-source repository.

Descriptive branding and environment-specific naming were neutralised
where those names were not runtime contracts. Runtime/integration
identifiers that form part of established behaviour were deliberately
not renamed merely for cosmetic consistency, avoiding unnecessary
contract breakage.

## 14. Release smoke testing

The release smoke test became a major release gate during the `v0.2.0`
development cycle.

The final baseline validates:

1.  required repository files;
2.  remediation catalogue consistency;
3.  Git whitespace integrity;
4.  absence of obvious tracked literal credentials;
5.  release-critical runtime and security regression tests;
6.  deployment contracts;
7.  PostgreSQL test availability;
8.  complete temporary-database reconstruction;
9.  reconstructed database invariants; and
10. Git release information.

Release-critical coverage includes remediation-controller runtime
semantics, deferred verification, Ansible Runner allowlisting, loopback
rejection, non-root Runner identity, non-root systemd identities,
verification gateway authentication, verification command safety, stdin
request transport, API authentication, Unified Finding schema
validation, seven scanner normalisation paths, Wazuh SCA API TLS
configuration, Wazuh Indexer TLS configuration and Wazuh Redis endpoint
configuration.

## 16. Security posture established by v0.2.0

Taken together, the changes establish important fail-closed properties:

-   unauthenticated callers cannot use remediation or verification APIs;
-   arbitrary Ansible playbooks cannot be selected through the Runner
    API;
-   loopback hosts cannot be supplied as remediation targets;
-   verification input is validated before command execution;
-   verification request data is transported structurally over stdin;
-   Wazuh API and Indexer TLS verification cannot be silently disabled;
-   the Ansible Runner does not require root container execution;
-   application systemd services do not require root execution;
-   unnecessary `NET_ADMIN` and privileged-container execution are
    rejected by release checks;
-   critical container/deployment versions are pinned;
-   invalid Unified Findings are rejected at ingestion; and
-   deferred verification requires sufficiently fresh scanner evidence.

These properties provide a stronger security boundary for future
platform expansion.

## 17. What v0.2.0 does not claim

`v0.2.0` should not be interpreted as a claim that the platform is
production-ready. It is a **pre-production hardened baseline**.

Areas suitable for later development or hardening include:

-   formal deployment provisioning and installation;
-   additional systemd sandboxing;
-   operational production validation;
-   asset management;
-   organisational/business context;
-   risk contextualisation;
-   threat-intelligence-assisted contextualisation;
-   scan coordination and asset coverage management; and
-   further correlation capabilities where they provide demonstrable
    value.

Minor housekeeping, such as stale comments/docstrings and obsolete
Compose metadata, is not considered a blocker for the baseline.

## 18. Transition to the next platform phase

The architectural focus after `v0.2.0` shifts from hardening the
existing finding-to-remediation pipeline toward adding the context
required for risk-driven remediation.

``` text
Asset Inventory / Asset Management
              |
              v
Scanner Orchestrators
              |
              v
Unified Security Finding
              |
              +------ Asset / Business Context
              |
              +------ Threat Intelligence
              |
              v
Risk Contextualisation
              |
              v
Contextual Risk and Remediation Priority
              |
              v
Deterministic Remediation Routing
              |
              v
Remediation
              |
              v
Two-Stage Verification
```

Asset management is the logical first capability because technical
severity alone does not establish organisational risk. Future
contextualisation needs authoritative information such as asset
identity, environment, ownership, business service, criticality,
exposure and data sensitivity.

This allows the platform to distinguish between the same technical
vulnerability occurring on a low-value test asset and on an
Internet-facing production system supporting a critical business
service.

## 19. Release significance

`v0.1.0` established the initial open-source remediation platform.

`v0.2.0` establishes a substantially more controlled and
regression-tested foundation for continued development. Its principal
contribution is not a single new feature, but a stronger set of
contracts around normalisation, routing, authentication, verification,
privilege, transport security, deployment and release reproducibility.

That hardened baseline is the foundation for the platform's next stage:
**asset-aware, context-driven cybersecurity remediation**.
